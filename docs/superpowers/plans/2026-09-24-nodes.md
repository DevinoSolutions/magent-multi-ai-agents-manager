# Nodes Implementation Plan (master)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run a project's whole Claude Code session on a pool machine (`devino-second`…`fifth`) under tmux, with git as the source of truth, transcripts/state pulled home, the existing attach supervisor as the local window, and `@nick` in the status bar.

**Architecture:** Four new leaf modules (`nodes.py` pure policy, `remote_mux.py` the single ssh/tmux/git seam, `node_scripts/*.sh` shipped over stdin, `node_sync.py` the daemon) plus `cli/node_cmd.py`; the launch path gains one dispatch branch; `attach_client` gains `--mux tmux`; `cli/attach` lifts its wt spawn into a shared function. Spec: `docs/superpowers/specs/2026-09-24-nodes-design.md` (decisions D1–D12 are settled).

**Tech Stack:** Python 3.10+ stdlib (`subprocess`, `shlex`, `tarfile`, `json`), click, bash scripts on the node, tmux, git, gh, Windows OpenSSH client. No new Python dependencies.

## 0. How this plan is executed (read before any task)

**Branching.** Every PR is a worktree under `C:/Users/amind/AppData/Local/Temp/mgtmp/wt-nodes-<pr>` branched from `feat/nodes`; never branch in the shared checkout. First command in a new worktree: `uv sync --extra dev` (a fresh worktree has no venv; `uv run` silently uses a global Python otherwise).

**Gate.** `uv run python scripts/check.py` (full) must print `GATE PASSED (FULL)` before each push. This desktop is out of RAM/CPU: run the full gate on `devino-fifth` (`~/work/magent` clone; make your own `git clone --shared` copy per task so agents don't collide), bring commits back with `git bundle`, push from the local worktree so the husky hooks run (pre-commit = fast gate locally, ~5 s; pre-push = full gate — if the local full gate is too heavy, run it on devino-fifth *first* and let the hook re-run it; never `--no-verify`).

**PR flow.** One PR per sub-plan, base `feat/nodes`, squash-merge only after the sub-plan's reviewers pass; CI is *informational* for this branch (user's fast-ship call, spec §17), but a red Windows leg is read, not ignored. `feat/nodes` → `main` + tag `3.20.0` only on the user's explicit release call.

**Laws that apply to every task (from CLAUDE.md; the reviewers check these):**
- `os.environ`/`os.getenv` only in `env.py`; `typing.Any` banned; `click.style` only via `magent.style`; no `sys.platform` capability checks in business logic; subsystems return data, `sys.exit` only in `cli/`.
- Heavy imports in `cli/` command modules are in-body with the `# heavy subsystem: in-body per policy` comment.
- `src/` never imports `cli/`. New leaves import only what spec §5 allows.
- Tests never touch the real `~/.magent`/`~/.claude`; never resolve the real `ssh`/`gh`/`git`-that-writes/`tmux`/`claude` — fakes on PATH only (`tests/unit/_fake_ssh.py` is created in PR-B and is THE fake; never write a second). `git` *read-only* on a tmp repo is fine.
- Every fixture that starts a real `serve`/`attention -d` sets `MAGENT_NODE_SYNC=0` alongside `MAGENT_HOTKEY_SUPERVISOR=0`, `MAGENT_UPLOAD_SUPERVISOR=0`, `MAGENT_PSMUX_BOOST=0`, `MAGENT_SESSION0_POLICY=allow`.
- Characterization tests are written and green BEFORE any refactor they pin (the attach lift in PR-C).
- `magent.config.example.json`, `cli/docs.py`, `.env.example`, `--help` snapshots are drift-pinned: change them in the same commit as the code.
- Conventional commits; no attribution lines.

## 1. Agent roles and models

| Role | Model | Why |
|---|---|---|
| Orchestrator (this session) | Fable 5.1 | Holds the spec, dispatches, reads reports, makes calls. Never edits code itself. |
| Sub-plan authors (one per PR, parallel) | **Opus 5.5** | They read real code and write complete code/tests into the sub-plan; wrong signatures here cost the most later. |
| Sub-plan consistency reviewer (one, after all sub-plans exist) | **Opus 5.5** | Cross-checks every signature/type/path across sub-plans against spec §4/§6 and each other. |
| Task implementers (fresh agent per task) | **Opus 5.5** | Implementation quality is the product; each task is TDD against a real, law-heavy codebase. |
| Mechanical tasks (drift files: example config, `cli/docs.py` tables, `.env.example`, CHANGELOG, README/CLAUDE.md bullets; migration stamp; help snapshots) | **Sonnet** | Well-specified, low-judgement edits with a test that says exactly when they're done. |
| Spec-compliance reviewer (per PR, stage 1) | **Opus 5.5** | Reads the diff against the sub-plan + spec; catches "not duplicated" violations and law breaches. |
| Code-quality reviewer (per PR, stage 2) | **Sonnet** | Naming, comment density, dead code, test smell; the codebase's style is explicit enough for it. |
| Gate runners / CI watchers / worktree cleanup / bundle shuttling | **Haiku** | Run a command, wait, report the result line; no judgement needed. Keep the wait loops off this desktop. |

Dispatch rule: a task goes to Sonnet only if its sub-plan marks it `[mechanical]`; everything else is Opus. A Haiku agent never edits a file.

## 3. Interfaces every sub-plan must honour (copied from the spec; a sub-plan may add, never rename)

