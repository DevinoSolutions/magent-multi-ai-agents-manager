The end state, in order:

````markdown
### The node is a checkout, not a mirror (2026-09-24)

This desktop runs about sixty agent sessions and was out of memory and CPU,
while four Linux machines the developer can already ssh into sat mostly idle.
A **node** is one of those machines running a project's WHOLE Claude Code
session under tmux, while this PC stays the place you look at it from, the
phone still reaches it, and a machine dying loses nothing. Neither remote
mechanism magent already had could be stretched to fit. A project's `host`
field runs its agent over a bare `ssh -t` with no multiplexer, so the agent dies
with the connection and nothing about it is durable. `magent attach` expects a
full magent install with its OWN config on the far side, and treats that config
as the truth; for a node the truth has to stay on this PC. The decisions below
(D1-D12 in `docs/superpowers/specs/2026-09-24-nodes-design.md`) are what make a
node its own thing rather than a third half-fit.

**Git is the truth, so there is no mirror (D1, D7).** A node holds a
`git clone` of the project's repo at the branch this PC is on, or, for a
workspace, one clone per child repo. Nothing is rsynced, nothing syncs in two
directions, and nothing locks the local folder. Mirroring the folder was the
obvious design, and it was rejected for its bug class, not its cost: a Windows
tree carries `node_modules` and virtualenvs built for win32, has no exec bits,
may be checked out with CRLF, lives under a cloud-synced folder with placeholder files and
sync locks, and the only rsync that runs here is cwRsync. Each of those turns
into a node-side failure that looks like the agent's fault. So work comes home
the way it already does: the agent commits and pushes, and this PC pulls. The
price is that the local tree must BE what its branch says. A bring-up refuses a
dirty tree, unpushed commits, a detached HEAD and a folder that is not a repo,
and each refusal names its fix (`git push -u origin <branch>`, or
`--allow-dirty`, after which those local edits are simply not on the node). The
far side gets the same rule: a node tree with uncommitted changes is refused
rather than checked over (`node tree dirty; recall or fix on the node`),
because silently discarding an agent's unpushed work is the one outcome worse
than a refusal.

**What git cannot carry is pushed one way at bring-up (D3).** A session cannot
work without its gitignored inputs, so `nodes.push_set` gathers them on this PC:
every ignored-and-untracked `.env` / `.env.*`, `.claude/settings.local.json`,
`CLAUDE.local.md` and `.mcp.json` (read from `git ls-files --others --ignored
--exclude-standard`, so a tracked file is never shipped and a tracked
`.env.example` never counts), the project's `push: [...]` extras, and its Claude
auto-memory directory re-keyed to the node's encoded remote dir. They travel as
one tar on the bring-up's stdin and land mode 0600. Keys and certificates are
opt-in through `push` and never auto-detected. `magent node plan` prints the set
and writes nothing; `magent node push` re-ships it to a live session after a
`.env` edit.

**Node-only data comes home, one way, all the time (D2).** Transcripts and the
node's `~/.magent/state/` exist only on the node, and a machine that dies would
take them with it. The sync daemon pulls both every `nodeSync.pullIntervalS`
(30s) into `~/.magent/nodes/<nick>/<sid>/`. Both are append-only by nature, so a
one-way copy cannot conflict, and that copy is what lets a session be resumed
somewhere else (`magent node recall`). It ships whole changed files, not deltas;
see the ledger.

**One person, one Unix user; root only for the hop that creates it (D4).**
`magent node setup` uses root once, to install packages, create the user and
authorize this PC's key. Every session after that runs as a dedicated
per-person user (`alice`, `bob`). On a machine other people also use, that is
what keeps credentials apart, bounds the blast radius of an agent's `rm`,
attributes every process to someone, and matches the per-user state layout
Claude Code already assumes. Sessions run as root only when `"user": "root"` is
written into that node's config, and even then `load_config` warns on every
load.

**Auth crosses; the Claude login does not (D5).** Every bring-up provisions the
node user's scope one way from this PC, content-hashed so an unchanged item
costs nothing: the `gh` token, `~/.claude/settings.json`, the user-scope MCP
servers that can work from there and their OAuth entries, the plugin list, the
skills directory, and magent's own node-side state hook wired with the same
event map as `magent hooks install`. Filters decide what "can work" means, and
each drop is printed with its reason, never silent. A hook whose command does
not resolve on the node is dropped, because a hook that cannot run fails every
turn. An MCP server ships only if it is a remote `http`/`sse` server
(`nodes.mcp_skip_reason` is the one classifier): a stdio server or one on this
PC's loopback would point at nothing on the node. The exception is the servers
named in the top-level `settings.mcpRelay`, which reach a node through a
bearer-checked relay route on `magent serve`; the relay's own §2 entry (plan K)
covers it. An MCP OAuth token the node has since refreshed is never overwritten. The
gh token ships only when this PC's `gh` names its account. The
Claude login is the one deliberate exception and is done by hand, once per node
(`ssh <user>@<host> claude`). Its refresh token has a single holder, and two
machines refreshing the same token log each other out. That is also why the
Claude OAuth block in `.credentials.json` is never copied, and neither are
`~/.ssh`, `ANTHROPIC_API_KEY` or anything under `~/.claude-swap-backup`. Secrets
travel on stdin, never in an argv (any user on a shared node can read argv from
`/proc`) and never in a log: `RemoteError` carries its command with the stdin
payload elided, and a unit test greps every argv the fake ssh recorded for the
fake token. The session itself inherits nothing from this PC. It gets the node
user's own login environment plus `LANG=C.UTF-8`, which is the opposite of the
local rule that `env.spawn_child_env` scrubs an inherited environment: there is
no inherited environment here to scrub.

**The node pushes with its own key (D6).** `node setup` generates an ed25519
key in the node user's home, where it stays, and registers it to the user's
GitHub account with `gh ssh-key add`. Agent forwarding was the easy answer and
the wrong one. A push has to work with no window attached, after this PC sleeps,
and from a bring-up started by the Session-0 hand-off, and none of those has an
agent to forward. A forwarded agent on a shared machine also lends this PC's key
to anyone with root there. Registering needs the `admin:public_key` scope on this
PC's `gh` login, which a default login lacks. `register_ssh_key` never raises:
the first real `node setup` stops at its `github-key` step and names the one-time
fix, `gh auth refresh -s admin:public_key`.

**Placement reads history, then sticks (D8).** `node: "<nick>"` pins a project
to a node. `node: "auto"` asks `nodes.place`, a pure function over the load
samples the daemon records (one every `nodeSync.sampleIntervalS`, kept for
`historyH`). The rejected version took one "least loaded right now" reading: a
machine someone else uses in bursts looks idle for exactly the second you ask,
and piling onto it is the outcome to avoid. So the score over the last 30
minutes is the p75 of load per core, plus a penalty when the window's peak
exceeds 1.5 times that p75 (someone's bursty session), plus memory pressure
below 15% free, plus a small term per session of this user's already there. A
node with fewer than five samples gets one live sample instead of a guess. Once
placed, a project stays put: the assignment lives in
`~/.magent/nodes/node-map.json` and wins until its node leaves the config. It is
machine state and is never written into the config. The pin is what the user
asked for; the assignment is a measurement.

**Four config keys and one stamp-only migration.** `settings.nodes` names the
machines, `settings.nodeSync` holds the three intervals, and a project gains
`node` and `push`. That is schema v4 on this branch, reached by
`_migrate_3_to_4`, which only stamps the number because every new key is
optional. The number is provisional in one known way: per-project account
routing also claimed v4 on `feat/account-routing`, so whichever of the two
branches merges into `main` second renumbers its own migration to 5 in an
isolated commit. A stamp-only migration is what keeps that a two-line change.
`node: "cloud"` shares the field but names no machine: it runs a Claude cloud
session in a local pane, and its own §2 entries explain it.

**The window is the attach supervisor, unchanged (D9).** A node session's local
window is the same `magent-attach-client` every `magent attach` pane runs, told
`--mux tmux`. That flag changes three strings, the remote attach command, the
out-of-band has-session probe and the corpse-scan marker, and one message: when
the supervisor stops, a node pane names plain `magent up` as the repair, not
`magent attach`, because a node has no magent install to attach to. `up` takes
no name: it is a top-up, and recreates only the sessions that are missing. The
reconnect ladder, the
probe-instead-of-exit-code rule, the one-line outage status and the ssh option
list (`SSH_CONNECTION_OPTS`, still the only one) took most of August to get
right, and a second reconnect loop written for nodes would have re-earned every
one of those bugs. The `wt` spawn was lifted out of `cli/attach._spawn_windows`
into `attach_client.spawn_attach_window` behind characterization pins written
first, so `magent attach`'s own windows are byte-for-byte what they were. It
lives in the leaf and not in `cli/` because its second caller,
`launch._dispatch_node_project`, is a src module, and a src module never imports
the cli package (LS-A-001).

**One tmux server per node user, sessions named by sid, targeted exactly
(D10).** Every node session lives on `tmux -L magent` under the name
`psmux.session_name` would give it locally, so the window title
(`magent:<sid>`), the session and the hotkey grammar keep one spelling. The
socket name has one owner, `attach_client.TMUX_SOCKET`, which `remote_mux`
re-exports. One socket is also what makes the phone work: `ssh` in, then
`tmux -L magent attach` opens the most recent session and `Ctrl+B s` lists every
one. Sharing a socket broke one assumption the local path relies on, and the
rule that replaces it is a law: **every tmux `-t` target is written `=<sid>`**,
tmux's exact-match form. A bare `-t <sid>` matches a PREFIX. That never mattered
locally, because psmux runs one session per socket. On a shared socket, a probe
for `api` answers yes while only `api2` is alive, so the supervisor reads a dead
pane as a deliberate detach and stops, and `attach -t api` lands in `api2`. So
the attach command, the has-session probe, the corpse marker
(`-L magent attach -t =<sid>`), `kill-session`, `send-keys`, `display-message`
and the targets inside `bring_up.sh` and `pull.sh` are all exact. Where the
target travels as a command STRING, it is also single-quoted:
`tmux -L magent attach -t '=<sid>'`. That string is parsed by the node user's
login shell, and zsh expands a bare `=word` as a command lookup, so an unquoted
`=api` would fail before tmux ever saw it. The corpse marker stays
`-L magent attach -t =<sid>`, and the scan accepts its quoted forms too.
`remote_mux.run` sidesteps the same trap for its own calls by wrapping the argv
in `bash -c`, so a node user's choice of shell never changes what runs. The status
bar says where a session is running: `psmux.status_brand(nick)` puts
` magent @second ` on the left. That is why a nick is ASCII `[a-z0-9-]` and at
most six characters: the bar is counted in cells, and the F1/F2 hints on its
right must still fit in 80 columns. Three nicks are reserved and can never name
a machine: `auto` (placement), `cloud` (the cloud backend) and `local` (the
directory `~/.magent/nodes/local/` holding this PC's own session snapshot).

**One seam to a node, and what it enforces.** `remote_mux.py` owns every
subprocess that touches a node: the ssh argv, `tmux -L magent`, git on the
node, the packaged scripts and the tar pull. It returns data or raises
`RemoteError`, and never prints or exits. Remote commands are `shlex.join` of a
list, never an f-string handed to a shell. Every call is bounded, and
`timeout_s` is keyword-mandatory so an unbounded call is a `TypeError`, not a
review comment. `BatchMode=yes` everywhere except the interactive window, which
is not this module. A step that must be atomic is ONE packaged bash script fed
on stdin (`bash -s -- <socket> <args>`, with any payload after a
`__MAGENT_PAYLOAD__` line). Every ENTRY script is fed through
`remote_mux.run_script` that way and includes `lib.sh` right after its `set`
line. `lib.sh` takes the tmux socket as a REQUIRED first argument with no
default, so the socket name the PC passes from `remote_mux.SOCKET` is the only
spelling that ever reaches a node. The three members of
`node_scripts.NON_ENTRY_SCRIPTS` never run alone, and `run_script` raises
`ValueError` for them. They travel inside other payloads: `lib.sh` is inlined
by the include, `provision.sh` installs `state_hook.sh` as a hook file, and
`setup.sh` and `doctor.sh` source `tmux_floor.sh`. Each logical step gets exactly one connection: Windows OpenSSH
has no `ControlMaster`, and sshd's `MaxStartups` throttles a burst of
unauthenticated connections. The same limit is why `launch` serializes
bring-ups per node behind a lock. `has_session` is tri-state, and answers
`None` when the probe itself failed and `False` only when tmux said no. It is
the lesson `psmux.live_sessions` already paid for: a dropped probe must never
read as a dead session.

**Two PCs, one node.** The desktop and the laptop share a config, so both may
bring the same project up on the same node. `bring_up.sh` asks `has-session`
first and ATTACHES instead of creating; the second PC's map records the entry as
`attached_existing`. Each PC's daemon pulls independently, which is safe because
the pull is idempotent, and the daemon takes the same per-node lock a bring-up
does, so a tick never races a bring-up's `git` on the same repo.

**The daemon that keeps the picture honest.** The sync daemon (`magent node
sync -d [--once] [--stop]`) makes one
ssh connection per node per tick. That connection lists the node's sessions
into `~/.magent/nodes/<nick>/sessions.json`, appends a load sample, and pulls
whatever transcripts and state files changed since the watermark in
`pull.json`. `status`, the session picker and `sessions --json` read node
liveness from that snapshot, not from a probe of their own, and a snapshot
older than twice the pull interval reads `stale`, never dead: a node that
stopped answering is not proof that its sessions stopped. An unreachable node
is logged once per change of state rather than once per tick, keeps its old
snapshot, and the loop moves on. A `RemoteError` never ends the loop; anything
else is logged at exception level and re-raised so Sentry sees it, as
`run_server` does. One constant, `node_sync.HEARTBEAT_NAME`, names the
daemon's heartbeat, its lock, its pid file and its thread, so no second
spelling can drift. `magent serve` supervises the daemon
(`upload_server._supervise_node_sync` calls `launch.ensure_node_sync`), exactly
as it supervises the Alt+V listener, gated on `MAGENT_NODE_SYNC` and on the
config having a `node` project at all. `status` exits 3 when the daemon is
stale. Like the other supervisor switches, `MAGENT_NODE_SYNC=0` is a
test-isolation law: a test that starts a real `serve` would otherwise start a
process that opens ssh connections to real machines, and no HOME redirect
contains a network.

**Four things the sync picture does not promise.** A new session's transcripts
arrive one tick late. The node reports its project's real path first, and only
the PC encodes that path into a transcript directory name (there is one encoder,
and it runs here), so the pull that can name the directory is the next one. A
node's state records carry the NODE's clock, so a record that looks stale may
only be clock skew between the two machines, and nothing here corrects for it.
A transcript that changed is re-sent whole, not as a delta; see the ledger. And
a call that times out counts as unreachable, exactly like a refused connection:
the daemon cannot tell a slow node from a gone one inside its bound, and
treating both the same keeps one code path.

**The daemon's lock exposed a bug in the lock.** Running a second daemon
against `lockfile.exclusive_lock` found that on POSIX a contender that FAILED to
acquire the lock unlinked the holder's lock file on its way out. A third process
then created a fresh file, took a fresh lock, and ran beside the holder. The
fix is PR-E's first commit, self-contained so it can be cherry-picked to `main`
as a hotfix, the second beside the project-dir encoder fix. Every existing
`exclusive_lock` user benefits, not just the node daemon.

**Recall, and the resume rule it depends on.** `magent node recall <project>`
pulls once more (an unreachable node means proceeding with what was already
pulled, and saying so), reports the last known commit per repo and whether the
node tree was dirty, kills the session, installs the transcripts and memory into
the destination's `~/.claude/projects/<encoded dir>/`, and clears the map
entry. `--to <nick>` then runs a normal bring-up with the newest transcript as
the resume id. `--local` prints `cd "<dir>"` and `claude --resume <id>` as two
separate lines after a `git pull` rather than launching anything, because the
user picks the terminal — never joined by `&&`, which Windows PowerShell 5.1
cannot parse; when `<dir>` is on another drive than the shell's (or the
shell's own folder is gone), a `(cmd.exe: use cd /d)` line follows the `cd`,
since cmd's plain `cd` does not switch drives. The encoded directory is Claude Code's rule, not magent's: every
UTF-16 unit outside `[A-Za-z0-9]` becomes `-`, and a name longer than 200 units
is cut there and suffixed with `-` plus a base-36 hash. The encoder magent
shipped before 3.20.0 kept `.` and `_`, which is wrong for most real
directories, so the fix landed first and on its own. There is exactly ONE
encoder, `sessions/claude.py::encode_claude_project_path`, and it runs on this
PC; `nodes.encoded_project_dir` delegates to it. Node scripts never encode.
They receive the finished name as an argument and refuse anything outside
`[A-Za-z0-9-]`, so a bad name can never write outside `~/.claude/projects`.
The encoder is pinned by vectors and by a unit test that reads this machine's
REAL `~/.claude/projects/` entries when there are some. `--to` ships the
transcripts in their own call, not inside the bring-up tarball. A first
bring-up of a fresh clone never runs `claude --continue`, which would error in
a directory with no session: it starts fresh, or resumes the pulled transcript
by id. The transcripts carry the node's `cwd`,
and recall never crashes on that: if `claude --resume` refuses them, recall
degrades to a message naming the directory they were installed in, for resuming
by hand.

**What is deliberately not here.** Production machines are not in the code at
all: a box like `root@prod-box` is simply not in anyone's pool (D11). Alt+V paste
into node panes, `send`/`model`/`peek` for node sessions and account routing for
node sessions were deferred to ship the core, and each has a ledger row (D12).
So are menu `u` and the F2 status-line flash for node sessions. The relay's
own entry, "The relay is token-gated; the upload page is not", covers why a
cloud session gets no MCP relay in 3.20.0 and ledgers it.

Proof: `tests/unit/test_config_nodes.py` (every validation rule and the
````

````markdown
When this PC runs out of memory and CPU, a project's whole agent session can run on another machine instead — any Linux box you can SSH into — while its window stays here, tiled with the rest, and reconnects on its own like any `magent attach` pane. magent calls such a machine a **node**.

| Field | Default | Description |
| --- | --- | --- |
| `settings.nodes.<nick>` | none | A machine. The nick is 1-6 characters of `a-z`, `0-9` and `-`, because it is shown in the session's status bar. `auto`, `cloud` and `local` are reserved and cannot name a machine. |

It installs tmux, git, curl and python3, creates your own Unix user, authorizes your SSH key, installs Claude Code and `gh` for that user, generates a GitHub key *on the node* (it never leaves the machine) and registers it to your GitHub account, then checks everything. Each step prints `ok`, `did` or `skip`, so running it again is safe. Every session afterwards runs as your user, never as root.

Registering the node's GitHub key needs one extra permission on this PC's `gh` login, which a default login does not have. The first `node setup` stops at its `github-key` step and tells you to run this once:

```bash
gh auth refresh -s admin:public_key
```

**Log in to Claude on each node yourself, once:**

```bash
ssh you@gpu-box.example.com claude
```

This is the one thing magent does not copy. A Claude login can only be held by one machine at a time; copying it would log out both this PC and the node. Everything else your sessions need does come across at every bring-up: your `gh` login, your Claude settings (minus any hook whose command is not installed on the node), your plugins, your skills, and magent's own state hook. Your user-level MCP servers come across when they can work from there, which means remote `http`/`sse` servers and their logins. A server that runs on this PC (stdio, or on `localhost`) is skipped on the node, with the reason printed, unless you list it in `settings.mcpRelay` (see [Browser tools on a node](#browser-tools-on-a-node)). Secrets travel over the SSH connection's input, never on a command line.

**Bring projects up as usual.** `magent --go`, the menu and `magent up` handle node projects alongside local ones. For each one magent clones or updates the checkout on the node, ships the gitignored files a session needs (`.env` and `.env.*`, `.claude/settings.local.json`, `CLAUDE.local.md`, an ignored `.mcp.json`, the project's Claude memory, and anything in `push`), starts the agent in a tmux session there, and opens a local window titled `magent:<name>`. The launch row shows `[@gpu]`, and the window's status bar reads ` magent @gpu `. If the session is already running there, started from another PC for example, magent attaches to it instead of starting a second one.

**Your work and your history come home.** The agent's commits come home through git. Its transcripts and agent states are pulled into `~/.magent/nodes/` every 30 seconds, so a machine that dies loses nothing and a session can be resumed elsewhere. `magent serve` keeps that sync running for you (`magent node sync -d [--once] [--stop]` runs, single-steps or stops it by hand; `MAGENT_NODE_SYNC=0` turns the supervision off). `magent status` exits 3 if the sync daemon has gone stale.

| `magent node recall <project> --to <nick>` | Move a session to another node and resume it there. |
| `magent node sync -d [--once] [--stop]` | Run the sync daemon yourself, run one pull and exit, or stop the running daemon. |
````
